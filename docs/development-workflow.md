# 飞书需求与 GitHub 交付

Agent Autoloop 提供调度与交付，GitHub 保存 Issue、PR 和 CI 结果。飞书只承担提需求、卡片确认与结果回写。

## 提需求

- 飞书允许名单与话题门禁通过后，把消息作为上游事件提交。中台确认接收后才推进游标；重投沿用消息 ID。
- 需求 Agent 按话题整理现状、改动范围、验收标准、验证方式、依赖，去掉原始消息里的私密数据。缺信息时只问影响实现的具体问题。
- 确认卡片绑定当前草稿版本。选择「确认执行」才加 `auto-agent-ready`，选择「仅建单」只发布 Issue，取消则结束该次确认。按飞书话题查重。

## 给 AI 派活

- 上游 Issue 轮询读取带执行标签的工单。Auto-Agent 在领取时重新核对目标仓库、批准的 Issue 正文和依赖。旧的批准凭据不授权人工后来扩大的范围。
- 每张被领取的 Issue 使用 `agent/issue-N` 分支、独立 worktree 和上游事项会话。互不依赖的 Issue 可并行，依赖未完成时等待 GitHub 状态变化。
- CI 或交付退回按 PR 和提交生成稳定的返工事件。旧交付状态仍在处理时先等它结束。新反馈走原工单、原分支和原 PR。

## 验收与合并

- 开发 Agent 提供 Issue 每条验收标准对应的结果、执行过的验证命令和提交 SHA。在 PR 中保留批准的范围和独立审查记录。未验证的必须项需要补齐。
- 上游 `delivery` 按 `main` 上的策略核对独立审查、目标分支、当前提交、必需检查及合并条件。普通路径通过后合并。授权、CI、发布和工作流配置等受保护路径走 `deliver-review`，由维护者合并。
- 正常完整交付使用 `Closes #编号`。合并和关闭均读回 GitHub 后按实际状态回写飞书；父 Issue 保留独立的整体验收。

## 本地验收

从两个独立的飞书话题开始。核对同一消息重发只产生一个 Issue，两张 Issue 在不同 worktree 开发。让其中一个 PR 的必需检查失败，确认原 PR 返工、新提交重查、另一张 Issue 独立推进。最后核对 GitHub 合并状态与飞书回写一致。
